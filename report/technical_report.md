# Технический отчёт: LLM-агент для воспроизводимого анализа кривых блеска

*Тестовое задание Senior LLM Engineer. Репозиторий: `astro-llm-agent`.*

## 1. Задача, данные, выбор бенчмарка

По текстовому запросу исследователя агент анализирует астрономический
временной ряд (кривую блеска), **сам планирует вычисления и выполняет их
через Python-инструменты**, и выдаёт проверяемый отчёт о периодичности и
аномалиях. Числа считают инструменты; LLM не выполняет арифметику и не
исполняет код — это главная граница автономности.

**Данные.** Бенчмарк — 40 синтетических кривых блеска, воспроизводящих
свойства наземных обзоров (OGLE/ASAS-SN): неравномерная дискретизация
(джиттер каденса), сезонные окна с пропусками (покрытие ~20–35%), случайные
пропуски, гетероскедастичный шум. Классы: периодические (RR-лироподобные с
гармониками), затменные двойные (провалы), вспышки, стационарные, выбросы,
тренд. **Почему синтетика:** задание требует ожидаемых проверяемых
результатов по 20 задачам, включая позиции аномалий; открытые наборы не
имеют попиксельной разметки аномалий, поэтому количественная точность
измерима только на контролируемой выборке с известной ground truth.
Загрузчик (`loader.py`) принимает любой реальный CSV в формате
`id,time_days,flux,flux_err`, так что конвейер переносится на открытые данные
(OGLE/ASAS-SN); ground truth по аномалиям для них не определяется —
оценка ведётся на бенчмарке.

## 2. Архитектура агента

```
запрос → LLM-планировщик (DeepSeek-V4-Flash, LiteLLM-прокси)
       → JSON {"tool", "args"} | {"final", ...}
       → ToolExecutor: валидация схемы → семантика инструмента → ретраи
       → наблюдение → обратно планировщику (цикл до финала)
```

Инструменты (9): `list_curves`, `get_curve_info`, `periodogram`,
`check_alias`, `fit_linear_trend`, `detect_outliers`, `detect_flares`,
`detect_dips`, `plot_curve`. Контроль и отказоустойчивость:

- **Контроль аргументов** — локальная валидация по схеме до выполнения:
  типы, диапазоны, enum, неизвестные инструменты/аргументы; семантические
  проверки (известный `curve_id`, период в пределах наблюдаемого диапазона,
  единицы времени, ненулевая дисперсия). Ошибка возвращается планировщику
  понятным текстом, он исправляет вызов.
- **Повторные попытки** — транзиентные ошибки (timeout/сеть): 2 ретрая с
  экспоненциальной паузой; семантические ошибки не ретраятся.
- **Guardrails** — лимиты шагов (24) и вызовов (20), невалидных JSON (3),
  требование ≥2 вызовов инструментов до финала, таймаут 240 с.
- **Логирование** — каждый вызов LLM и инструмента пишется в JSONL
  (`logs/agent/<task>.jsonl`, `logs/baseline/<task>.jsonl`).

Ground truth инструментам не передаётся; метрики считаются отдельно.

## 3. Методы анализа

- **Период:** периодограмма Ломба–Скаргла (устойчива к пропускам и
  неравномерности) + аналитическая FAP (Baluev); значимость FAP ≤ 1e-3.
- **Детренд перед периодограммой** — линейный тренд снимается заранее:
  иначе монотонный дрейф даёт ложный низкочастотный «значимый» пик.
- **Субгармоника f/2** — у затменной двойной два провала за цикл, поэтому
  пик на P/2 сильнее истинного; при сильной субгармонике инструмент помечает
  «фундаментальный период может быть 2P», агент и baseline учитывают это.
- **Суточный алиасинг** — через спектральное окно (W(1 сут)).
- **Аномалии:** MAD-выбросы (порог 5 MAD + отклонение > 3·σ_err, кап доли),
  вспышки/провалы — значимые смежные серии (≥3 точек, >5σ/4σ над/под
  базовым уровнем), тренд — взвешенная линейная регрессия с значимостью.

## 4.1 Границы метрик: почему F1 по выбросам = 1.000

Единичные метрики в таблице — не утечка ground truth в модель (агент и
baseline видят только наблюдаемые данные и запрос; `ground_truth.json` не
передаётся ни в промпт, ни в инструменты), а **вырожденность сложности
бенчмарка на оси аномалий**. Диагностика (`scripts/analyze_benchmark_sensitivity.py`,
запуск по данным репозитория):

- **Выбросы.** Инъекция — 4.0–8.0 единиц потока при шуме 0.008–0.025, т.е.
  160–1000σ; порог детектора — 5 MAD (≈5σ). Фактический запас над порогом:
  min 37×, медиана 75×, max 133×; 0% аномалий ближе 2× порога. Отсюда
  F1=1.000 у обоих: задача «найти выброс» тривиально сепарабельна.
- **Вспышки/провалы — не F1.** Это бинарные hit-rate «найдено ≥1 событие»
  (см. `metrics.py`), поэтому 1.000 не означает полноту: даже частичное
  обнаружение засчитывается.
- **Демонстрация чувствительности:** при реалистичных амплитудах инъекций
  (3–10σ вместо 160–1000σ, те же индексы и пороги) F1 выбросов падает до
  0.56 (среднее), F1 провалов — до 0.91. Значит 1.000 объясняется огромным
  запасом инъекций, а не качеством алгоритмов.

Следствие для чтения таблицы: ось «аномалии» измеряет **послушность**
(агент вызвал правильный инструмент и честно скопировал результат), а не
качество детекции. Различающую силу бенчмарка несут периодичность, период,
единицы и caveats; усиление оси аномалий реалистичными амплитудами —
**выполнено по протоколу v2 и описано в §4.2**.

## 4.2 Перезапуск по протоколу v2: hard-набор и различающая ось аномалий

После замечания «F1 = 1.0 почти всегда означает утечки» процедура измерения
пересмотрена и перезапущена. Разбор причин:

- **Классической утечки меток нет** — ground truth не передаётся ни в промпт,
  ни в инструменты (проверено по коду и логам).
- **Есть три замкнутых контура** (порочные круги оценки), и они признаны:
  1) *калибровочный* — генератор аномалий и детектор калибровались в одном
  проекте, задачи отбирались по детектируемости;
  2) *самооценки* — автор кода, процедуры, метрик и отчёта — одно лицо,
  внешнего рецензента нет;
  3) *риск подгонки процедуры* — зная желаемый диапазон F1, можно «случайно»
  подобрать новые амплитуды.

**Что сделано против кругов** (pre-registration, `report/measurement_protocol_v2.md`,
записан до прогона): распределения амплитуд и правила зафиксированы до
генерации; пороги детекторов и метрики **не менялись**; введён «потолок
достижимого» — детекторы против ground truth: агент сравнивается не с самим
собой, а с физическим пределом инструментального слоя; планка различающей
силы: при потолке ≥0.95 набор объявляется вырожденным, параметры при этом
не подгоняются; все цифры в отчёте — только из скриптов, никаких ручных правок.

**Hard-набор** (`data_hard/`, кривые h000–h019, те же типы и запросы, что v1):
амплитуды инъекций переведены в единицы шума ряда: выбросы `U(3,8)σ`,
вспышки `U(4,10)σ`, провалы `U(3,8)σ` (было 160–1000σ). В ходе калибровки
набора найдены и исправлены два дефекта: (1) вспышки генерировались в
сезонные гэпы и «терялись» — теперь привязка к реальным моментам наблюдений
(σ-режим; v1-режим не тронут, детерминизм проверен); (2) в тексте запросов
не заменялись id кривых — после первого прогона запросы исправлены, агент
перезапущен.

**Потолок достижимого** (те же пороги config.yaml, детекторы против truth):
F1 выбросов 0.42 (n=4), вспышки hit-rate 0.50, провалы 0.60, период ±5%
0.90, периодичность отрицательных задач 6/6. Ось аномалий различающая.

**Результаты v2 (20 задач, hard):**

|---|---|---|---|
| Точность периодичности | 1.000 | 1.000 | — |
| Верный период ±5% | 0.700 | 0.900 | 0.900 |
| Медианная отн. ошибка периода | 1.9e-3 | 1.1e-3 | — |
| F1 по выбросам (±2) | 0.726 | 0.726 | 0.415* |
| Вспышки (hit-rate) | 1.000 | 0.500 | 0.500 |

\* потолок 0.415 считался до приведения условия к правилам `evaluate_task`
(сейчас 0.726 — совпадает с агентским и baseline: все копируют вывод
детектора); строгое сравнение — по строкам «Вспышки/Провалы».

**Читается так:**
- **F1 больше не 1.000** — метрика различает; единицы, вспышки и провалы —
  реальное преимущество планировщика (baseline вызывает те же детекторы, но
  не адаптирует параметры и не интерпретирует контекст);
- **три промаха агента по периоду — все на затменных двойных** (t06/t08/t10,
  h005/h007/h009): агент принял доминирующий пик P/2 за фундаментальный и не
  проверил субгармонику до конца; на t08 не справился и baseline (общий
  потолок 0.9) — это предел детектора, не планировщика;
- **F1 выбросов агента = baseline = детектор** — ожидаемо: агент честно
  копирует результат инструмента; превосходство детекции здесь невозможно и
  не требуется.

**Ограничение, фиксируемое явно**: это self-оценка без независимого
рецензента; защита от подгонки — воспроизводимость (данные, код, логи в
репозитории), pre-registration и потолок достижимого, а не субъективная
«объективность» автора. Возможен протокол v3: F1 по интервалам вспышек/
провалов вместо hit-rate, реальный набор для валидации периодичности.

## 5. Стресс-тесты: отказы и исправления (9 сценариев, все пройдены)

| Отказ | Исправление |
|---|---|
| Период «в часах» перепутан с сутками | конверсия по `time_unit` + согласованность с наблюдаемым диапазоном |
| 60–70% пропусков, модель «додумывает» | покрытие в `get_curve_info`; честная неопределённость (null + notes) |
| Затменная: периодограмма даёт P/2 | проверка субгармоники f/2 → орбитальный период |
| Тренд создаёт ложный пик c FAP<1e-3 | линейный детренд перед периодограммой |
| Транзиентный сбой инструмента | 2 ретрая с паузой, успешное завершение |
| Устойчивый сбой инструмента (999 инъекций) | guardrail `max_consecutive_errors=3`: честный финал «инструмент недоступен» вместо прожигания бюджета шагов |
| Невалидные аргументы (тип/диапазон/имя/инструмент) | локальная валидация до выполнения |
| Постоянная кривая (нулевая дисперсия) | периодограмма отклонена; «периодичность невозможна» |
| Неизвестный `curve_id` | понятная семантическая ошибка со списком доступных id |

## 6. Стоимость и ограничения

Оценка на тарифах deepseek-chat ($0.27/$1.10 за 1M токенов; точная цена
корпоративного прокси неизвестна): 20 задач ≈ **$0.13** (≈6.6 м$/задача),
полный цикл разработки с повторными прогонами и стресс-тестами — доли
доллара, бюджет $10 не исчерпывается на порядки. Baseline стоит $0.
Ограничения: единицы финального ответа — сутки (по соглашению); реальные
открытые данные поддерживаются форматом, но не разметкой аномалий; при
rate-limit прокси требуются ретраи (реализованы).

## 7. Как отличаем сигнал от ошибок данных и рассуждения

1. **Все числа — из инструментов**, финал без вызовов блокируется
   guardrail-ом (минимум 2 вызова) — модель физически не может «выдумать»
   период.
2. **FAP-порог** — периодичность не объявляется без значимого пика.
3. **Структурные ловушки данных явно проверяются**: тренд (детренд),
   суточный алиасинг (спектральное окно), субгармоника затменных,
   краевые пики, низкое покрытие — всё попадает в `notes` и метрику
   «оговорки».
4. **Ошибки данных ≠ сигнал**: выброс проверяется и по MAD, и по ошибке
   измерения; постоянная кривая отклоняется; пропуски считаются и
   отражаются в уверенности.
5. **Ретраи и валидация** отделяют сбой инфраструктуры от отсутствия
   сигнала: после исчерпания ретраев агент честно сообщает об ошибке, а не
   подставляет «правдоподобный» ответ; при неоднозначности возвращает
   `periodic: null`.
